# M2: HTTP, authentication, TLS and response inspection

Status: in progress, delivered in focused PRs. This record does not declare the full milestone complete.

## Slice 1: Request preparation and structured forms

HTTP-01–03, AUTH-01 and RESP-03: preserve an existing percent-encoded URL query rather than decoding and rewriting it when adding fields. New query fields use UTF-8 percent encoding, including literal plus and spaces; repeated names and empty values are retained. Disabled/blank-key rows are ignored and fragments are removed before execution. User headers override defaults; repeated user header names are explicitly rejected.

Body modes distinguish None, explicit raw text (including empty text) and structured form fields. Existing version-one requests without the optional mode retain their prior empty/nonempty raw-body behavior. Changing mode retains inactive data. Structured forms preserve order and repeated keys, encode spaces as plus and literal plus as `%2B`, and own their `application/x-www-form-urlencoded` content type. GET/HEAD bodies fail visibly before transport rather than relying on undocumented URLSession behavior.

API-key auth supports a header or query. Selected Basic/Bearer/API-key auth overrides its matching user header. A query API key replaces all matching existing and added keys, preserving unrelated URL encoding. Key values use the same Keychain-backed credential field as Basic/Bearer and are omitted from native exports/backups. Ordinary fields remain plain text as disclosed. UTF-8 Basic auth and header validation are tested.

Each exchange records a summary of the actual initial prepared URLRequest used for execution, before redirects and transport-added fields. The Request inspector masks query values and custom header values, records body size without body content, and explains timing granularity. It also displays the effective response URL. This inspector is not a content-free diagnostic: URL paths, query names, standard headers and effective response URLs can contain user data. Total elapsed time is measured; DNS/connect/TLS phases are not instrumented. No general request preview/export or execution timeline is claimed yet.

Eight new tests bring the suite to 64 passing cases. Tests cover all methods/body policy, preservation of existing escapes, duplicate and empty query/form values, API-key replacement and injection errors, UTF-8 Basic, legacy workspace round trips, masked prepared metadata, and real loopback wire bytes. The earlier nested-variable test now uses POST to comply with the explicit body policy.

## Slice 2: Streaming binary and multipart uploads

HTTP-04/05: selectable binary files and ordered, enabled/disabled multipart text/JSON/file parts. Each file reference persists its resolved path, size, modification date and file identity. Missing/unreadable/non-regular files fail visibly; changed files must be selected again. Export/backup retains references and metadata rather than attaching local files. The part editor works on a copy with Apply/Cancel, preserving inactive settings.

`RequestEngine.freeze` owns a private `0600` temporary body snapshot. It reads file chunks of 64 KiB, checks file metadata before/after reading, bounds the complete upload at 256 MiB, and supplies a replayable InputStream with the exact Content-Length. Multipart owns its generated Content-Type/boundary; names, filenames and MIME values reject control characters and quoted fields escape quotes/backslashes. JSON parts use application/json. No file is loaded whole into the URLRequest body. This trades temporary disk space for a stable replayable wire body; it is not direct zero-copy streaming from a mutable source file.

Normal completion, preparation errors and cancellation remove temporary bodies. Forced process termination can leave private files in the OS temporary directory until it is cleaned; this implementation does not promise secure erasure or crash-time cleanup. Selected file paths are not templated or auto-read until Send. Imported references require local file identity/size/time to match before sending.

Same-origin redirects follow URLSession behavior and can request a fresh body stream. Cross-origin redirects stop at the redirect response, preventing automatic forwarding of API-key headers and upload bodies. The policy also applies to ordinary HTTP requests. It is not an interactive cross-origin redirect approval flow.

Seven upload/wire cases plus an exact-budget test bring the suite to 72 cases. Tests cover private snapshots/cleanup, missing and changed files, boundary/header/filename fidelity, order and disabled parts, template expansion, injection rejection, file-reference round trips/duplication/backups, exact/overflow budgets and actual streaming redirect replay. Installed-app file picker, part Apply/Cancel, large-file cancellation and permission-dialog checks remain pending; HTTP-04/05 stay partial.

## Slice 3: Reusable authentication and named secrets

AUTH-02/03/06: independently named None/Basic/Bearer/API-key profiles with a selected profile reference per request. Profiles contain metadata and a named-secret reference; they never embed secret values. Selecting a profile overrides request-specific auth while retaining inactive settings. Deleted/missing profiles fail visibly rather than reverting to another credential source. Deleting a profile leaves references explicit until the user changes selection.

Native secret create/replace/delete uses Keychain service `app.rill.namedsecrets`. The manager never displays existing secret values. `{{secret:name}}` works directly or through nested environment indirection in request composition and upload part text. Secret bytes are opaque, so braces inside a token are not recursively evaluated. Each request's resolver freezes a secret on first use for consistency across fields, holds it only in memory, and never copies it into workspace environment maps.

Secret names are 1–128 ASCII letters/digits/dots/hyphens/underscores. Native metadata takes precedence over the process provider; an empty/missing/denied native item is an error and cannot fall back. Without native metadata, the read-only provider resolves `RILL_SECRET_` plus uppercase name with dots/hyphens replaced by underscores. Normalization collisions in the native catalog are rejected. Process values are captured at resolver creation; restart the app after changing its process environment. The provider has no write/delete API. Removing native metadata makes process fallback eligible, disclosed in the delete confirmation.

Workspace/export/backup stores only profile and secret descriptors. Imported descriptors receive fresh identities; normalized name collisions are renamed and profile/environment/request template references remapped. Imported named secrets must be configured locally before sending; imported descriptors cannot reuse the source's Keychain UUID. References without incoming descriptors may resolve a deliberately configured local/process name when Send is chosen. Metadata persistence retains existing workspace conflict checks; native value updates are individual Keychain operations, not a multi-store transaction or compare-and-swap API.

Seven fresh tests bring the suite to 79 passing cases: provider precedence and denial, normalized names, opaque/frozen values and indirection, profile precedence/missing cases, vault CRUD, absence of seeded values from workspace/backups, and collision-safe imported identities/references. Actual Keychain permission prompts, profile manager focus and process-launched installed-app checks remain pending. AUTH-02/03/06 stay partial. OAuth2 and named TLS profiles remain subsequent slices.

## Slice 4: Explicit OAuth2 acquisition

AUTH-04/05: profile-configured client credentials and authorization code with S256 PKCE. Token endpoints require HTTPS except literal loopback test addresses, use ephemeral sessions with a 30-second timeout, reject redirects and enforce a 64 KiB response cap including received bytes. Client authentication supports form-encoded Basic or POST-body secrets from named providers; public-client mode is allowed for code exchange, not client credentials. Scope is explicit. Error responses are mapped to generic errors without logging provider content.

Browser authorization generates cryptographically random 32-byte state and verifier values, opens the system browser, and binds an ephemeral IPv4-only listener to 127.0.0.1. Register `http://127.0.0.1:{dynamic-port}/oauth/callback` with the provider. The listener checks Host/path/state and duplicate callback parameters, caps headers at 16 KiB/eight connections, closes slow connections after five seconds, and stops after success, rejection, cancellation or the three-minute authorization deadline. It accepts one authorization outcome; wrong-path requests do not complete the flow. It is not an embedded browser or LAN server. IPv6 callback binding is not implemented.

Acquired bearer access tokens go directly to the profile's named native Keychain entry. Client-secret and access-token entry names must differ. Token values, authorization codes, state/verifiers and provider response bodies are not written to workspace files or reports. Expiry metadata is saved and expired OAuth profiles reject Send. Missing expiry is disclosed. There is no automatic acquisition, refresh-token retention, implicit grant, discovery or automatic refresh. Done/Cancel/quit cancels the flow; a token Keychain write remains an individual store operation, not part of a multi-store transaction.

The suite now has 89 tests: ten OAuth cases cover the RFC S256 vector, independent random sessions, authorization URL fields, state/path/duplicate/error and plus-encoding rejection, confidential/public token request rules, token validation/expiry, real loopback callbacks, listener shutdown/cancellation/timeout, real client-credentials/code exchanges, and redirect/oversize/provider-error rejection. Provider/browser interoperability and installed-app cancellation/Keychain checks remain pending, so AUTH-04/05 remain partial.

The independent implementation was checked against primary specifications on 2026-10-24: [OAuth2 RFC 6749](https://www.rfc-editor.org/rfc/rfc6749), [PKCE RFC 7636](https://www.rfc-editor.org/rfc/rfc7636), [native apps RFC 8252](https://www.rfc-editor.org/rfc/rfc8252) and [security BCP RFC 9700](https://www.rfc-editor.org/rfc/rfc9700). These links describe the underlying protocols; Rill does not claim to implement every extension or every BCP recommendation.

## Slice 5: Named TLS profiles and client identities

TLS-01–03: requests select system defaults or an independent named profile. Custom trust supports up to 16 bounded DER/PEM anchors, optional system roots and explicit hostname verification through Security.framework SSL policies. Missing profile/required identity fails rather than silently using defaults. Custom trust does not fetch missing chain certificates from the network. Profiles do not change global system trust.

The explicit Insecure development mode belongs to one profile, appears with warnings in the manager/request selector, and asks for confirmation on each desktop Send. It disables both certificate and hostname verification for that selected request. It never changes the default policy or OAuth's independent token transport.

Client identities can be selected from macOS Keychain or explicitly imported from a password-protected PKCS#12 file into the default Keychain. Passwords are used for import only and never persisted by Rill. Workspace profiles store a persistent identity reference/label and public anchors, not private keys. Imported workspaces remap profile IDs and clear foreign identity references while retaining the requirement to select an identity locally. Deleting a profile does not remove imported Keychain identities. OAuth token acquisition currently retains its separate system-trust transport; TLS profiles apply to ordinary request execution.

Tests generate disposable certificate authorities, a localhost server and an mTLS server on loopback. The full suite passes 95 cases, including six TLS cases: default trust rejects the fixture before and after a custom-trust success; hostname mismatch fails; explicit insecure mode succeeds; mTLS fails without an identity and succeeds with a memory-only fixture identity; DER/PEM/bounds and missing-profile checks; import requires identity reselection; malformed PKCS#12 errors omit the passphrase. Fixture identities are not imported into a personal Keychain. The memory-only test path requires macOS 15 (all current CI configurations); actual macOS 14 Keychain identity import remains manual acceptance.

Implementation uses the installed Apple SDK's Security.framework interfaces and their documented availability (`SecTrustSetPolicies`, anchor APIs, `SecPKCS12Import`, persistent identity references). The test-only certificate generator uses the host OpenSSL executable; no OpenSSL library, generated key or certificate is bundled into Rill. Installed-app permission prompts, real provider chains/identities, macOS 14 and upgrade behavior remain pending; TLS rows stay partial.
