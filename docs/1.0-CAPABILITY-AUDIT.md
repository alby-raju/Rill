# 1.0 capability audit: local API development and CI

Dated 30 October 2026. The owner selected local API development and CI before hosted collaboration and cross-platform desktop applications. This is a source-oriented triage and acceptance inventory, not a claim of complete Postman/HTTPie parity or a release announcement. Delivery order remains authoritative in [ROADMAP.md](../ROADMAP.md).

## What the 122 rows mean

The preserved [baseline checklist](CAPABILITIES.csv) has **3 verified, 118 partial and 1 deviation**. Partial mixes implemented behavior awaiting independent/manual acceptance with genuinely missing behavior. It is not a missing-feature count. Do not convert these counts to a compatibility percentage.

The [122-row audit](1.0-capability-audit.csv) retains each original ID, status and acceptance target, adds implementation/test starting points and records concrete known gaps where established. A source directory or test filename is a navigation aid, not evidence that every acceptance sentence is covered. This audit does not change baseline sign-off. Existing protocol capabilities still need their own acceptance; concentrating new development on HTTP does not silently waive them.

## Competition comparison boundaries

Primary documentation checked on the audit date identifies concrete workflow gaps:

- Postman's collection runner combines ordered requests, scripts, data inputs and cookie handling; those must be evaluated as one workflow, not a list of similarly named controls. [Collection Runner documentation](https://learning.postman.com/docs/tests-and-scripts/running-collections/intro-to-collection-runs).
- Postman's CLI supports local collection execution and several local report formats. Our direct file runner and HTML reporting remain distinct deliverables. [CLI execution](https://learning.postman.com/docs/postman-cli/postman-cli-run-collection), [CLI reporters](https://learning.postman.com/docs/postman-cli/postman-cli-reporters).
- HTTPie's CLI documents request construction, offline inspection, downloads and session persistence. Rill has ad-hoc execution, but that does not establish session/download/CLI grammar parity. [HTTPie CLI documentation](https://httpie.io/docs/cli).

These references define scenarios to test; they are not a promise to copy every product feature. The initial supported desktop is macOS. A portable Linux CLI needs implementation and distribution evidence before Linux CI support can be claimed; a successful macOS runner is not portable CI acceptance.

## How a capability closes

For each original row: inspect the implementation, identify exact behavior and limits, link the focused success/failure/cancellation/boundary tests, run an independent or manual scenario where required, and record revision/artifact/service/OS evidence. Only then update the baseline status. Keep approved deviations explicit. All inherited public capabilities need behavior evidence or an owner-approved scope decision before the final 1.0 sign-off; no version-only promotion.

The release-critical sequence and concrete gates live in [the roadmap](../ROADMAP.md). Architecture decisions, compatibility reports and new PRs should reference original capability IDs as well as roadmap milestone names because the historical `CLI-01` ID and roadmap `CLI-01` task refer to different scopes.
